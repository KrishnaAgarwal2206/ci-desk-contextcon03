    Backup & Migrations¶

    This page covers the database's storage model, the current (partially adopted) migration strategy, how to create and apply schema changes, and how to back up and restore the database and blob artifacts. Read Deployment first if you have not chosen an environment yet.

    The database¶

    • Local: SQLite at data/ci_local.db (DATABASE_URL=sqlite:///./data/ci_local.db). The engine (app/db/session.py) opens SQLite with check_same_thread=False, timeout=120, and a connect-time PRAGMA setting journal_mode=WAL, synchronous=NORMAL, busy_timeout=120000. WAL mode means the on-disk database is accompanied by -wal and -shm sidecar files — include those when copying a live database.
    • In-memory: sqlite:///:memory: uses a StaticPool (critical for tests to share one connection).
    • Production: Azure SQL, via a SQLAlchemy-compatible DATABASE_URL. Models are portable SQLAlchemy 2.0; the WAL/StaticPool specifics are SQLite-only.

    Warning

    Never commit data/*.db. The local database contains real competitor data and is gitignored. The same applies to blob artifacts under LOCAL_BLOB_ROOT — treat them as sensitive.

    Migrations: the reality¶

    Schema management is partially migrated to Alembic. In practice the schema is created and evolved two ways:

    1. Base.metadata.create_all() — run by both ci-agent init-db and at server startup. This creates any missing tables from app/db/models.py.
    2. _safe_add_columns — idempotent column additions applied in code for incremental fields.

    Alembic (alembic.ini, alembic/) is present and wired (target_metadata = Base.metadata, NullPool), but the revision chain is minimal:

    • ec80a363b261_initial_schema — down_revision = None, an empty placeholder stub.
    • b3f2a8c94d12_admin_control_plane — the current head. Hand-written and idempotent (guarded by table_exists / index_exists / column_exists). Adds source_schedules, scan_requests, competitor_news_profiles, competitor_profile_versions, admin_audit_logs, and the source_scan_logs.news_profile_version_id column.

    Note

    Because most tables are born from create_all(), an autogenerated Alembic migration on a fresh checkout may see the schema as already up to date. Alembic is the intended long-term path but is not yet the source of truth. See Release Notes for this drift item.

    Create and apply migrations¶

    To add a schema change through Alembic:

    # 1. Edit models in app/db/models.py, then autogenerate a revision
alembic revision --autogenerate -m "add my_new_table"

# 2. Review the generated script under alembic/versions/ before applying

# 3. Apply to head
alembic upgrade head

    You can also apply migrations through the CLI, which combines table creation with the Alembic upgrade:

    ci-agent init-db --alembic     # create_all + _safe_add_columns, then alembic upgrade head

    Plain ci-agent init-db (no flag) runs create_all + _safe_add_columns only, which is sufficient for local development and for standing up a fresh database.

    Tip

    If you hit "no such column" or similar schema errors after pulling changes, run ci-agent init-db (or alembic upgrade head) to bring the local schema forward. See Troubleshooting.

    Backing up blobs¶

    Raw and normalized artifacts (fetched HTML, JSON, cleaned text) are stored in the blob store, not the database — the DB holds only URIs.

    • Local: artifacts live under LOCAL_BLOB_ROOT (default ./data/blob), referenced as local://<path>. Back up by copying that directory alongside the database.
    • Azure Blob: artifacts live in the AZURE_BLOB_CONTAINER (default ci-artifacts), referenced as azblob://<container>/<path>. Use standard Azure Blob backup / lifecycle / geo-replication policies.

    A consistent backup is database + blob store together — the URIs in the DB must resolve to objects that still exist in the blob store.

    Restoring¶

    To restore a local environment:

    1. Stop the server and any worker processes (so nothing holds the SQLite lock).
    2. Restore data/ci_local.db plus its -wal and -shm sidecar files (or checkpoint the WAL before backing up so the main file is complete).
    3. Restore the LOCAL_BLOB_ROOT directory so artifact URIs resolve.
    4. Restart and confirm health with ci-agent status and the Monitoring screens.

    For Azure, restore the Azure SQL database from its point-in-time backup and ensure the blob container is at a matching point in time so azblob:// URIs remain valid.
