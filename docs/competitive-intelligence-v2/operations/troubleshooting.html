    Troubleshooting¶

    This page is a symptom-driven runbook for the most common failure modes. Each entry follows a symptom → cause → fix structure. For deeper recovery of a specific failed run, see Recover a Failed Run; for error semantics, see Error Handling, Retries & Status Codes.

    No signals produced¶

    Symptom: A scan completes successfully but list-candidate-signals (or the Signals screen) is empty.

    Cause: Two common reasons:

    1. First scan is a baseline. Every analyzer's first pass over a source emits only a baseline_created delta and no candidate signals — there is no previous state to diff against. Signals appear on the second and later scans, once there is something to compare.
    2. Mock provider produces limited output. With LLM_PROVIDER=mock and NEWS_PROVIDER=mock, adapters and analyzers return deterministic fixtures, not live content. Real signals require real providers.

    Fix: Run the scan a second time so there is a baseline to diff against. If you need real intelligence, switch to real providers (LLM_PROVIDER=azure_openai, NEWS_PROVIDER=tavily + TAVILY_API_KEY) — see Configuration.

    Jobs not running (stuck as pending/enqueued)¶

    Symptom: You submit a scan request (or run schedule-once), it returns success, but jobs never move past pending and no results appear.

    Cause: In server mode nothing consumes the queue. The FastAPI server and admin scan-requests only enqueue jobs. The server-side scheduler starts only the WeeklyDigestScheduler, not a scan worker.

    Fix: Run a worker to drain the queue:

    ci-agent worker-once      # process the enqueued jobs
# or the all-in-one local run:
ci-agent dev-run-once     # schedule + fetch + analyze

    In production, ensure a separate Service Bus consumer process is running. See Deployment → The worker in production.

    Warning

    This is the single most common "nothing is happening" cause. If a run sits idle, first confirm a worker/consumer is actually running.

    LLM errors (content filter, truncation, empty output)¶

    Symptom: A step ran but produced no useful result; a DetectedChange has an empty impact assessment, or an LLMTrace shows an error_message.

    Cause: The LLM call hit a content_filter block or was truncated by the length limit, or returned non-JSON. The provider is designed to never crash the pipeline — on any of these it returns an LLMResult with an error_message and an empty output_json (non-JSON responses are captured as {"raw_text": ...}).

    Fix: Inspect the LLMTrace / LLMCostLedger for the affected step (LLM screen or GET /admin/observability/llm-runs). For truncation on the large steps (impact_analysis, competitor_query, maintenance_copilot, final_classifier), note they already use max_completion_tokens=4096; other prompts use 1024. For content-filter blocks, adjust the input payload or re-run. The pipeline continues regardless — downstream steps fall back (for example, _fallback_impact when impact LLM output is absent).

    Info

    Empty output_json with a populated error_message is expected, non-fatal behavior — not a crash. Treat it as a data-quality signal for that one item, not a pipeline outage.

    Duplicate competitors¶

    Symptom: After loading config more than once, the same competitor (and its sources) appears multiple times.

    Cause: load-config (app/admin/yaml_loader.py) always inserts — there is no upsert or dedup. Re-running it against the same YAML creates duplicate Competitor and Source rows.

    Fix: Load config only once per environment. To fix existing duplicates, soft-delete the extras via the Admin Control Plane (DELETE /admin/competitors/{id}) or the panel. When iterating on config, prefer editing existing competitors/sources through the API/panel rather than reloading the YAML. See Add a Competitor & Sources.

    Schema errors¶

    Symptom: Errors like "no such column" or "no such table" after pulling changes or upgrading.

    Cause: The local database predates a model change. Schema is managed mostly by create_all + _safe_add_columns (Alembic is only partially adopted).

    Fix:

    ci-agent init-db            # create_all + _safe_add_columns
# or, if using Alembic:
alembic upgrade head
# or both together:
ci-agent init-db --alembic

    See Backup & Migrations for the full picture.

    Email not sending¶

    Symptom: Digest assembly succeeds and creates a WeeklyDigest, but no email arrives; delivery logs show the send was skipped.

    Cause: SMTP_HOST is unset. EmailDelivery intentionally skips sending (status skipped, logged to DeliveryLog) when SMTP_HOST is empty.

    Fix: Set the SMTP settings: SMTP_HOST, SMTP_PORT (465 uses SSL, otherwise STARTTLS), SMTP_USER, SMTP_PASSWORD, SMTP_FROM_EMAIL, and DEFAULT_RECIPIENTS. Then re-send. See Assemble & Send a Weekly Digest.

    Info

    The email client builds a permissive SSL context (check_hostname=False, CERT_NONE) on purpose, for the corporate proxy environment. This is deliberate — do not "fix" it.

    Panel data missing¶

    Symptom: The Live Run flowchart or pipeline board shows no data, or stages are blank, even though runs exist.

    Cause: Usually one of:

    1. Stage-key format was changed. The pipeline board keys per-competitor statuses as workflow:stage (e.g. layer2:classification) and per-stage rollups as workflow:stage:agent_name. The stage comes from AgentRunTelemetry.stage, not agent_name. The panel JS depends on this exact format — a change breaks rendering.
    2. No telemetry rows. If runs executed outside observe_agent (or the DB session factory was not wired), there are no AgentRunTelemetry rows to aggregate.

    Fix: Do not change the workflow:stage key format. Confirm runs are producing AgentRunTelemetry rows (LLM/Runs screens or GET /admin/observability/pipeline-board). Confirm the correct pipeline_run_id / scan_run_id is selected.

    Danger

    Never change the workflow:stage key format. It is load-bearing for the admin panel JavaScript and there is no fallback.
