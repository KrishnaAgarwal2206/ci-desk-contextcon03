    Deployment¶

    This page covers how to run the Competitive Intelligence Aggregator in production: switching from the local development stack to Azure-backed infrastructure, running the scan worker as a separate process, scheduling automated scans, understanding what happens at server startup, and publishing this documentation site.

    For the exhaustive list of environment keys referenced here, see the Configuration & Environment reference.

    Environments: local vs production¶

    The application selects its infrastructure at runtime through app/infra.py, driven by the ENVIRONMENT setting and the presence of Azure connection strings. There is no separate "prod build" — the same code runs both places and swaps implementations based on configuration.

    Concern Local (ENVIRONMENT=local) Production (ENVIRONMENT=production)
    Queue InMemorySourceScanQueue AzureServiceBusSourceScanQueue
    Blob store LocalBlobStore (under LOCAL_BLOB_ROOT) AzureBlobStore
    LLM provider MockLLMProvider (or Azure OpenAI if keyed) AzureOpenAIProvider
    Database SQLite (data/ci_local.db, WAL mode) Azure SQL (SQLAlchemy-compatible)
    Config source .env file Azure Key Vault → environment

    The selection logic is deliberately conservative: build_blob_store() and build_queue() return the Azure implementation only when ENVIRONMENT is not local AND the relevant connection string is set. If either condition is missing, they fall back to the local implementation. This means setting ENVIRONMENT=production alone is not enough — you must also provide the connection strings.

    # Production environment (values are placeholders — never commit real secrets)
ENVIRONMENT=production
DATABASE_URL=mssql+pyodbc://<user>:<pw>@<server>.database.windows.net/<db>?driver=ODBC+Driver+18+for+SQL+Server

LLM_PROVIDER=azure_openai
AZURE_OPENAI_ENDPOINT=https://<your-resource>.openai.azure.com
AZURE_OPENAI_API_KEY=<key>
AZURE_OPENAI_MODEL=gpt-4o

AZURE_SERVICE_BUS_CONNECTION_STRING=<connection-string>
AZURE_SERVICE_BUS_QUEUE_NAME=source-scan-jobs

AZURE_BLOB_CONNECTION_STRING=<connection-string>
AZURE_BLOB_CONTAINER=ci-artifacts

    Danger

    Never print, log, or commit real secrets. Use placeholders like <key> and https://<your-resource>.openai.azure.com in any file that lands in the repo. .env is gitignored; .env.example is the safe template. In production, prefer Azure Key Vault over a .env file.

    Azure-ready swaps¶

    Each infrastructure dependency is behind a small interface so the local and Azure implementations are interchangeable. To move to Azure, set the environment (above) — no code change is required.

    • Queue → Azure Service Bus. AzureServiceBusSourceScanQueue (app/queue/azure_service_bus.py) serializes jobs as JSON bodies and uses lock-token ack / abandon / dead_letter semantics. Queue name defaults to source-scan-jobs.
    • Blob → Azure Blob. AzureBlobStore (app/storage/azure_blob.py) stores artifacts as azblob://<container>/<path>; the local store uses local://<path>. Container defaults to ci-artifacts.
    • LLM → Azure OpenAI. AzureOpenAIProvider (app/llm/azure_openai_provider.py) lazily constructs an openai.AzureOpenAI client (api-version 2024-08-01-preview), calls the deployment named by AZURE_OPENAI_MODEL, and writes an LLMCostLedger row per call. See LLM Abstraction.
    • Database → Azure SQL. Point DATABASE_URL at Azure SQL. Models are SQLAlchemy 2.0 and portable; note the SQLite-specific WAL/StaticPool behavior only applies to the local file/in-memory DB.

    The worker in production¶

    Warning

    In server mode, nothing consumes the queue automatically. The FastAPI server (and admin scan-requests) only enqueue jobs. The server-side scheduler (app/scheduler/__init__.py) starts a WeeklyDigestScheduler only — it does not periodically run source scans or drain the queue. You must run a worker/consumer separately, or jobs will sit unprocessed.

    In production the pattern is a separate process consuming the Azure Service Bus queue and running SourceScanWorker.process_job for each message. Locally, the equivalent is CLI-driven execution:

    # Local: enqueue due sources, then drain the queue in one process
ci-agent schedule-once    # enqueue only
ci-agent worker-once      # process queue only

# Or the all-in-one local run
ci-agent dev-run-once     # schedule + fetch + analyze

    ci-agent <cmd> is equivalent to python -m app.cli <cmd>. See the CLI Reference and Run a Manual Scan.

    Scheduled scans¶

    Two independent schedulers exist:

    • Layer 1 source scans are driven by SourceSchedule rows (one per source) and get_due_sources(). On the server these only advance schedules and enqueue — they still require a worker to execute. For unattended runs on Windows, run_daily_scan.bat is provided at the repo root and is ready to register with Windows Task Scheduler for a daily full scan.
    :: run_daily_scan.bat — register with Windows Task Scheduler for a daily scan
    • Weekly digest is handled by the in-server WeeklyDigestScheduler, which fires Mondays at 08:00 (Asia/Kolkata) to assemble and send the weekly digest via Layer 3 delivery. See Assemble & Send a Weekly Digest.

    Note

    The WeeklyDigestScheduler is the only thing the server-side scheduler starts. It does not run scans. Treat source-scan scheduling (Task Scheduler / a Service Bus consumer) as a separate deployment concern.

    Startup behavior¶

    When the FastAPI app boots (app/main.py), the startup hook performs several one-time actions:

    1. Base.metadata.create_all() — creates any missing tables (schema is primarily managed this way plus _safe_add_columns, not Alembic; see Backup & Migrations).
    2. Starts the scheduler — the WeeklyDigestScheduler described above.
    3. Seeds the price catalog — _seed_price_catalog() inserts an active LLMPriceCatalog row (USD/1k: input 0.005, output 0.015, cached 0.0025) so cost tracking works immediately.
    4. Wires the DB session factory into the LLM provider so per-call LLMCostLedger rows can be written.
    5. Orphan cleanup — marks any PipelineRun / ScanRun / AgentRunTelemetry rows still in running state (left over from a crash or restart) as interrupted.

    Warning

    Startup uses the deprecated FastAPI on_event hook rather than the newer lifespan handler. This is a known drift item (see Release Notes); it works but should be migrated.

    Publishing these docs¶

    This documentation site is built with MkDocs Material and published as a static site through Azure DevOps.

    pip install mkdocs-material
mkdocs build            # renders docs/ into static site/
# publish the site/ directory via the Azure DevOps pipeline

    mkdocs build produces a self-contained site/ directory. Point the Azure DevOps release/pipeline at that folder to publish. Use mkdocs serve locally for a live preview while editing.
