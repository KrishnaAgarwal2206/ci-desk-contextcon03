    Manual Run Console¶

    The Manual Run Console (admin-scan-console, loader loadAdminScanConsole) is the panel's cockpit for triggering scans on demand. From one form you choose one of six request types, the console builds the right parameters, submits the request, and then polls until the run finishes. This page walks through opening the console, the six request types and their parameter builders, what happens after you submit, and how to watch the run to completion.

    Opening the console¶

    Select Admin Control → Scan Console in the left rail. The form presents a request-type selector; the JavaScript shows or hides the extra inputs (a competitor picker, a source-ID field) depending on the type you choose, assembles a params_json object, and posts it.

    The 6 request types and their param builders¶

    All six are handled server-side in _run_scan_in_background. The console builds params_json per type:

    Request type What it does params_json
    all_sources Enqueue every active source (schedule_scan(None)) {}
    competitor_sources Enqueue all active sources for one competitor { "competitor_id": ... }
    single_source Enqueue one source { "source_id": ... }
    layer2_only Run the Layer 2 orchestrator only, skipping the queue { "scan_run_id"?, "competitor_id"?, "limit"? }
    retry_failed Re-enqueue the failed SourceScanLog rows of a prior run { "scan_run_id": ... }
    rebaseline Clear last_scan_at, then enqueue { "source_id": ... }

    The console shows the competitor picker for competitor_sources and the source-ID field for single_source and rebaseline.

    layer2_only bypasses the queue

    Queue-based types (all_sources, competitor_sources, single_source, retry_failed, rebaseline) enqueue jobs via schedule_scan and need a worker to consume the queue. layer2_only instead calls the CoreIntelligenceOrchestrator.run directly and does not touch the queue.

    Submitting and status transitions¶

    Submitting posts to the scan-request endpoint, which accepts the work immediately and returns 202:

    POST /admin/scan-requests
{ "request_type": "...", "params_json": { ... }, "requested_by": "admin" }

    The response is a ScanRequestOut with status = "created". The background task then advances the request through its lifecycle:

    created → running → completed   (with scan_run_id)
                 → failed        (with error_message)

    The server only enqueues

    Except for layer2_only, submitting a request enqueues jobs but does not execute them. A worker (CLI worker-once, or a Service Bus consumer in production) must be running for queued jobs to actually run. See Run a Manual Scan.

    Watching the run¶

    After submitting, the console polls GET /admin/scan-requests?limit=20 to track the request itself. The Live Run and Scan Runs views poll the run-visibility endpoints:

    • GET /admin/runs/current — the latest running (or most recent) run, with total/completed/failed job counts
    • GET /admin/runs/{id} — a specific run
    • GET /admin/runs/{id}/jobs — the per-source SourceScanLog rows, each resolved with source name/type, competitor name, status, timestamps, adapter name, attempt count, error_type, error_message, and candidate_signals_count

    The jobs view is where you diagnose a partially failed run — see Recover a Failed Run.

    D17 — Manual run lifecycle¶

    sequenceDiagram
    participant UI as Console (UI)
    participant API as scan_request_routes
    participant BG as BackgroundTasks
    participant ORCH as Orchestrator / Queue
    participant DB as DB

    UI->>API: POST /admin/scan-requests
    API-->>UI: 202 ScanRequestOut (status=created)
    API->>BG: _run_scan_in_background
    BG->>DB: status = running
    alt layer2_only
        BG->>ORCH: CoreIntelligenceOrchestrator.run (skip queue)
    else queue types
        BG->>ORCH: schedule_scan (enqueue jobs)
    end
    ORCH-->>BG: result
    BG->>DB: status = completed (+scan_run_id) / failed (+error_message)
    loop poll
        UI->>API: GET /admin/scan-requests?limit=20
        UI->>API: GET /admin/runs/{id}/jobs
        API-->>UI: status + per-source job rows
    end
