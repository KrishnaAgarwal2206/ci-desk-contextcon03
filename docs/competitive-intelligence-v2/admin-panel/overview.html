    Panel Overview & Navigation¶

    The admin panel is the operator's cockpit for the Competitive Intelligence Aggregator. It is a single, self-contained HTML file served by the FastAPI app that surfaces every part of the system — dashboards, the intelligence feed, feedback and governance tooling, deep observability, and the admin control plane — across 32 screens grouped into 7 functional areas. This page explains how the panel is served, the design system it uses, the full screen map, the frontend patterns every screen shares, and how a click travels all the way to the database.

    What the panel is¶

    The entire panel is one file, scripts/admin_panel.html (~371 KB, ~6000 lines), with all CSS and JavaScript inline. There is no build step — no bundler, no framework, no npm install. The FastAPI app reads the file at request time and returns it as an HTMLResponse:

    # app/main.py:36-38
@app.get("/admin/panel")
def admin_panel():
    return HTMLResponse(_PANEL_HTML.read_text(...))

    Open it in a browser once the server is running:

    http://localhost:8000/admin/panel

    The app is titled "Competitive Intelligence Aggregator" (v0.1.0) and mounts seven routers, each backing one theme of the panel:

    Router variable File URL theme
    router app/admin/routes.py /health, competitors, sources, scan-runs
    intelligence_router app/admin/intelligence_routes.py scoring, agents, changes, query, digests, feedback governance
    observability_router app/admin/observability_routes.py /admin/observability/*
    policy_health_router app/admin/policy_health_routes.py /admin/policy-health/*
    schedule_router app/admin/schedule_routes.py source schedules
    scan_request_router app/admin/scan_request_routes.py manual scan requests, run visibility, audit logs
    news_profile_router app/admin/news_profile_routes.py news profiles + versioning

    All routers live under app/admin/

    There is no app/api/ directory. In particular, the observability endpoints live in app/admin/observability_routes.py, not app/api/.

    Design system¶

    The panel uses its own slate-dark palette defined in CSS variables:

    --dark:  #0d1117;   /* page background      */
--mid:   #161b22;   /* raised surfaces      */
--panel: #21262d;   /* cards / panels       */
--border:#30363d;   /* dividers             */
--text:  #e6edf3;   /* primary text         */

    Categorical accents for charts, chips, and per-competitor colour coding come from COMP_COLORS:

    COMP_COLORS = ['#58a6ff','#3fb950','#f78166','#d29922','#c084fc','#38d9a9','#ff9e7b'];

    The panel theme is not the Godrej brand

    This dark developer theme is an internal operator tool and is deliberately distinct from the organisation's black-and-white brand system. Do not treat the panel palette as brand guidance; it exists purely for at-a-glance readability of dense operational data.

    The 7 groups and 32 screens¶

    Navigation is a left rail. Selecting an item calls navigate(sec), which toggles the active section and invokes that screen's loader. The groups and their screens:

    Group Screens
    Overview dashboard, pipeline-health
    Intelligence changes, query, profiles
    Feedback & Tuning scoring, agents, suppressions
    Governance nl-command, governance, patterns, rule-library, weights-editor, policy-packs, policy-health, runtime-state
    Observability obs-live-run, obs-health, obs-runs, obs-sources, obs-llm, obs-incidents, obs-copilot, obs-costs, obs-agent-load
    Delivery digests, delivery-logs
    Admin Control admin-competitors, admin-sources, admin-schedules, admin-scan-console, admin-runs, admin-news-profiles, admin-audit-log

    Each group maps to the deep-dive pages in this section: Intelligence Screens, Governance Screens, Observability Screens, the Manual Run Console, and the Admin Control Plane.

    Frontend patterns¶

    Every screen is built from a handful of shared helpers, so learning one screen teaches you all of them.

    • apiFetch(path, opts) — the single HTTP helper. It prepends apiBase(), sets the JSON Content-Type, stringifies non-string bodies, throws Error("<status>: <text>") on any non-OK response, and returns parsed JSON (or text). A known fix ensures it does not double-stringify a body that is already a string.
    • sections / sectionLoaders / navigate(sec) — sections maps each screen name to its DOM container; sectionLoaders maps each screen name to its data-loading function. navigate(sec) toggles .nav-item.active / .section.active on #section-<sec>, sets #page-title, and calls sectionLoaders[sec](). This is the entire routing model.
    • statusChip(s) and badge helpers — statusChip, badgeSig, badgeStatus, badgeActive, adminAlert, and showAlert render coloured status pills and inline alerts from a status string via CSS variables.
    • No authentication — the panel sends no auth headers, and the API uses permissive CORS (*).

    No authentication — trusted network only

    The panel and its API have no login and open CORS. This is safe only on a trusted internal network. Never expose /admin/panel or the API to the public internet.

    Costs throughout the panel are shown in both USD and INR (the ledger applies a fixed USD_TO_INR = 85 conversion).

    Request flow¶

    When you interact with a screen, the click reaches the database along one of three paths: a plain read/write through a router and the repositories layer; an LLM-backed endpoint that calls build_llm_provider().complete_json; or a scan request that is accepted immediately (202) and executed in the background.

    D15 — Request flow¶

    flowchart TD
    UI["Panel screen<br/>admin_panel.html"] --> AF["apiFetch(path)"]
    AF --> R["FastAPI router<br/>app/admin/*.py"]
    R --> V["Pydantic schema<br/>+ repositories.py"]
    V --> DB[("SQLite / Azure SQL")]

    R -->|LLM endpoints| LLM["build_llm_provider()<br/>.complete_json"]
    LLM --> DB

    R -->|scan requests| BG["BackgroundTasks<br/>_run_scan_in_background"]
    BG --> Q["Queue"]
    Q --> W["Worker"]
    W --> TC["observe_agent →<br/>AgentRunTelemetry / LLMCostLedger"]
    TC --> DB

    The startup sequence (app/main.py:46-69) prepares this flow: it runs create_all, starts the scheduler, seeds the LLMPriceCatalog, wires the DB session factory into the LLM provider for the cost ledger, and marks any orphaned running PipelineRun / ScanRun / AgentRunTelemetry rows as interrupted. The server also shares a single InMemorySourceScanQueue via set_queue and set_scan_request_queue.
