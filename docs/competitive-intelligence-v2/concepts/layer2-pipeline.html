    Layer 2 — Intelligence Pipeline¶

    Layer 2 is the multi-step pipeline that converts raw CandidateSignal rows from Layer 1 into deduplicated, classified, scored, and impact-assessed DetectedChange records — plus delivery artifacts and a cumulative CompetitorProfile. This page explains the 15-step orchestrator, which steps use the LLM, and how deduplication and clustering work.

    Grounded in Godrej Consumer Products

    Every LLM prompt in this pipeline is written for Godrej Consumer Products (GCP) as the home company; the monitored competitors are HUL, P&G India, ITC, Marico, Dabur, and Reckitt. The impact_analysis prompt (v2) hardcodes GCP brand, category, and market lists plus grounding rules. This is the app's internal domain framing — distinct from the documentation site's branding.

    Purpose and role¶

    The input is CandidateSignal rows with status candidate or promoted_to_layer_2_pending. The output chain is: CandidateSignal → NormalizedSignal → EventCluster → FinalClassification → SignificanceScore → ImpactAssessment → DetectedChange, followed by delivery preparation, profile patching, and historical indexing. The code lives in app/intelligence/ (roughly 21 files).

    The orchestrator¶

    CoreIntelligenceOrchestrator (app/intelligence/orchestrator.py) is constructed with a Session and an optional LLM provider, and lazily loads the single active ScoringWeightProfile. The entry point is:

    process_candidate_signals(candidate_signal_ids=None, scan_run_id=None, limit=100, pipeline_run_id=None) -> CoreIntelligenceRunResult

    It loads signals, creates or attaches a PipelineRun, groups signals by competitor_id (one CompetitorRun each), and processes each signal through _process_one (steps 1–8). It commits after every signal to release the SQLite write lock between LLM calls; a failed signal is rolled back individually and recorded in result.failures. The returned CoreIntelligenceRunResult carries counters for everything created (normalized signals, clusters, detected changes, alerts, digest entries, profile patches, LLM calls, failures).

    The full pipeline¶

    Steps 1–8 (_process_one) run per signal; steps 9–15 (_process_cluster) run once the signal has joined a cluster. Five steps can invoke the LLM (marked in green); the rest are deterministic. Three decision points can short-circuit the flow.

    Signal-level steps (1–8)¶

    # Step File / function LLM?
    1 Intake validation intake.py validate_candidate() No
    2 Load related inline (Competitor + Source) No
    3 Evidence hydration evidence.py build_evidence_bundle() No
    4 Signal normalization normalization.py normalize_signal() Yes (conditional)
    5 Quality routing quality_router.py route_signal() No
    6 Atomic claims atomic_claims.py build_atomic_claims() No
    7 Fingerprinting fingerprinting.py build_fingerprint() No
    8 Clustering clustering.py find_or_create_cluster() Yes (conditional merge judge)

    Intake checks status, evidence, IDs, non-blank title/summary/type, and confidence ≥ 0.25; invalid signals are archived with status needs_review. Evidence hydration classifies source authority (official → first_party → reputable_news → third_party_news → social → careers → weak_snippet → unknown). Normalization does a deterministic first pass and only calls the LLM when needs_llm(). Quality routing promotes on official/reputable + confidence ≥ 0.45, high-value category + confidence ≥ 0.45, or confidence ≥ 0.55; suppress/archive_only short-circuits.

    Cluster-level steps (9–15)¶

    # Step File / function LLM?
    9 Final classification classification.py classify_cluster() Yes (conditional)
    10 Significance scoring scoring.py score_cluster() No (deterministic)
    11 Impact assessment impact.py build_impact_assessment() Yes (primary)
    12 DetectedChange upsert inline No
    13 Delivery preparation delivery_router.py prepare_delivery() No
    14 Profile patch + narrative profile_updates.py Yes (narrative only)
    15 Historical index historical_index.py No

    Classification runs _rules_classify first (majority vote) and only calls the final_classifier LLM when the category is None, confidence < 0.6, or there are more than two candidates. Scoring is fully deterministic (see Scoring & Impact) and its band decides the DetectedChange status: Archive → archived, otherwise ready. Impact assessment is the only step that consumes the cumulative CompetitorProfile plus recent-change history, producing trend-aware GCP-specific analysis. Delivery preparation emits an AlertCandidate and/or DigestEntryDraft by band (High → both; Medium → digest, alert only if threat_level == "direct"; Low → digest only if enabled; Archive → nothing). The profile patch is applied immediately so later clusters in the same run see the updated profile.

    reasoning.py record_trace() writes ReasoningTrace audit rows at intake, evidence, normalization, quality routing, clustering, classification, scoring, and detected-change build.

    Deduplication and clustering¶

    Clustering is two-tier deterministic-first. build_fingerprint() normalizes the entity (stripping suffixes like ltd/pvt/inc), slugs the action and category, and buckets the date monthly to produce a stable event_fingerprint (generic entities get a signal-scoped hash suffix). find_or_create_cluster() then tries: (1) exact fingerprint match on (competitor_id, event_fingerprint); (2) deterministic fuzzy match over the 50 most-recent non-archived clusters (same action, ≥2 shared entity words, within ±14 days, compatible category); (3) the event_merge_judge LLM for ties, which merges only when same_event is true and confidence ≥ 0.7 (conservative). DetectedChange is upserted per cluster.

    LLM usage in the pipeline¶

    Step Prompt / version Output
    Normalization (4) signal_normalizer v1 event action, claim status, normalized summary, confidence
    Clustering (8) event_merge_judge v1 same_event, reason, confidence
    Classification (9) final_classifier v1 final category, confidence, reason
    Impact (11) impact_analysis v2 headline, summary, so_what, recommended_action, threat_level, watchpoints, affected GCP categories/markets
    Profile narrative (14) profile_narrative v1 3–4 sentence executive narrative

    The impact_analysis system prompt hardcodes GCP identity, brand/category/market lists, 15 grounding rules, and an exact output-key contract. See LLM Abstraction for the full catalog.
