    Layer 1 — Source Scanning¶

    Layer 1 is the ingestion and first-pass extraction stage. For each due Source, a source-type-specific adapter fetches raw data, the worker persists it, and a matching analyzer diffs it against the previous scan and applies a cheap deterministic gate (with optional LLM assistance) to produce CandidateSignal rows — the input to Layer 2. This page explains the adapter and analyzer patterns, the scan worker, and how work is scheduled and queued.

    Purpose and role¶

    The unit of work is a Source (a website page, a website crawl scope, a news search, a careers page, a blog/RSS feed, or a social channel) belonging to a Competitor. The output is CandidateSignal rows with status candidate. The orchestration boundary is SourceScanWorker.process_job().

    Layer 1 end-to-end¶

    The path from a due source to a persisted candidate signal is deterministic-first: cheap checks run before any LLM call, and the first scan of a source only establishes a baseline.

    flowchart TD
  classDef llm fill:#efe,stroke:#3fb950,color:#111
  A["schedule_scan"] --> B["get_due_sources"]
  B --> C["create SourceScanLog<br/>+ SourceScanJob"]
  C --> D["Queue.enqueue"]
  D --> E["SourceScanWorker.process_job"]
  E --> F["AdapterRegistry<br/>resolve by source_type"]
  F --> G["Adapter.scan → AdapterScanResult"]
  G --> H["persist raw artifacts → BlobStore"]
  H --> I["persist normalized docs + blocks"]
  I --> J["upsert source items"]
  J --> K["AnalyzerRegistry<br/>resolve by source_type"]
  K --> L["Analyzer.analyze"]
  L --> M{cheap gate}
  M -->|suppress_noise| N["drop / note"]
  M -->|candidate_without_llm| P["CandidateSignal draft"]
  M -->|llm_review| Q["LLM prompt"]:::llm
  Q --> P
  P --> R["persist_analysis_result"]
  R --> S[("DB: CandidateSignal")]
  S --> T["Layer 2"]

    The adapter pattern¶

    The contract is app/adapters/base.py: SourceAdapter.scan(source, competitor, context) -> AdapterScanResult. Adapters are stateless — configuration comes from source.config_json plus get_settings(). Every adapter returns an AdapterScanResult (app/schemas/adapter.py) carrying fetched_artifacts, normalized_documents, and discovered_items (each item requires a fingerprint).

    The registry (app/adapters/registry.py) maps source types to adapters:

    Source type Adapter File
    website_page, website_scope WebsiteAdapter app/adapters/website/adapter.py
    news_search NewsSearchAdapter app/adapters/news/adapter.py
    careers CareersAdapter app/adapters/careers/adapter.py
    blog, social BlogSocialAdapter app/adapters/blog_social/adapter.py

    Behavior differs by type: website_page does a single GET; website_scope does a depth-1 BFS crawl honoring POLITENESS_DELAY_SECONDS; news_search runs search-provider queries (no page fetch); careers detects the ATS and dispatches to a connector; blog parses RSS or an HTML index; social dispatches to LinkedIn/Twitter providers or deterministic mock posts.

    Adapters do no LLM work

    Adapters only fetch and normalize. All LLM assistance happens in the analyzer stage. All adapter HTTP uses httpx with verify=False (deliberate, corporate proxy).

    Connectors and providers (adapter dispatch)¶

    Within an adapter, a second dispatch chooses the concrete connector or provider. For news and social the choice is by configured provider or auto-detection (search providers skip keys that start with PASTE); for careers it is by ATS detection with a Playwright fallback.

    flowchart TD
  ST{source_type}
  ST --> WEB["website_page / website_scope<br/>WebsiteAdapter"]

  ST --> NEWS["news_search<br/>NewsSearchAdapter"]
  NEWS --> N1["Bing"]
  NEWS --> N2["Tavily"]
  NEWS --> N3["Brave"]
  NEWS --> N4["Mock"]

  ST --> CAR["careers<br/>CareersAdapter"]
  CAR --> C1["Greenhouse"]
  CAR --> C2["Lever"]
  CAR --> C3["Workday → generic HTML"]
  CAR --> C4["Generic HTML + Playwright fallback"]

  ST --> BLG["blog<br/>BlogSocialAdapter"]
  BLG --> B1["RSS / Atom parse"]
  BLG --> B2["HTML index parse"]

  ST --> SOC["social<br/>BlogSocialAdapter"]
  SOC --> S1["LinkedIn (Apify)"]
  SOC --> S2["Twitter (Apify)"]
  SOC --> S3["mock posts"]

    News provider auto-detect priority is Bing → Tavily → Brave → Mock. A missing social key produces a warning, not a failure.

    The analyzer pattern¶

    The contract is app/analysis/contracts.py: SourceAnalyzer.analyze(source, competitor, scan_run, adapter_result, persisted_scan_objects, repositories, llm_provider) -> SourceAnalysisResult. The registry (app/analysis/registry.py) mirrors the adapter registry by source type.

    Every analyzer follows the same shape: fetch previous state via repository lambdas → detect deltas (the first scan emits only a baseline_created delta and no signals) → run the cheap gate (app/analysis/cheap_gate.py, returning no_action / suppress_noise / llm_review / candidate_without_llm) → on llm_review call the LLM → build a CandidateSignalDraft.

    First scan is baseline only

    Because change detection diffs against a prior scan, the very first scan of a source records a baseline and produces no candidate signals. Signals appear from the second scan onward.

    The scan worker flow¶

    SourceScanWorker.process_job() (app/workers/source_scan_worker.py) runs a 12-step sequence. The adapter and analyzer each run inside their own observe_agent() telemetry span, and error handling is asymmetric: pre-flight failures retry, while adapter/analyzer runtime failures acknowledge without retry.

    sequenceDiagram
  participant Q as Queue
  participant W as SourceScanWorker
  participant AD as Adapter
  participant DB as DB / BlobStore
  participant AN as Analyzer
  participant LLM as LLMProvider
  Q->>W: receive(job)
  W->>DB: load source + competitor
  alt missing source/competitor
    W->>DB: mark_scan_log_failed(NotFound)
    W->>Q: ack
  else resolved
    W->>DB: mark_scan_log_running
    Note over W,AD: observe_agent(adapter, layer1, source_type)
    W->>AD: scan()
    alt adapter raises
      W->>DB: _fail_job (mark failed)
      W->>Q: retry
    else success
      AD-->>W: AdapterScanResult
      W->>DB: persist raw / docs / items
      Note over W,AN: observe_agent(analyzer, source_type_analyze)
      W->>AN: analyze()
      AN->>LLM: complete_json (only on llm_review)
      LLM-->>AN: LLMResult (or error_message)
      AN-->>W: SourceAnalysisResult
      W->>DB: persist_analysis_result
      W->>DB: mark_scan_log_success + counts
      W->>Q: ack
    end
  end

    Retry acknowledgement asymmetry

    _fail_job marks the log failed and calls queue.retry, which increments the attempt count and dead-letters after MAX_QUEUE_ATTEMPTS (default 3). But adapter/analyzer runtime failures ack the message (no retry) — only pre-flight failures (for example a missing adapter registration) retry. LLM failures never crash the pipeline; the provider returns an LLMResult with error_message and empty output_json. See Error Handling, Retries & Status Codes.

    Scheduling and queueing¶

    SourceSchedule holds one row per source (schedule_type manual/hourly/daily/weekly/cron, next_run_at indexed). get_due_sources() (app/scheduler/due_sources.py) selects schedules whose next_run_at is in the past, adds the source, and immediately advances next_run_at to prevent double-enqueue. schedule_scan() (app/scheduler/service.py) then creates a ScanRun, a SourceScanLog and SourceScanJob per source, and enqueues each job.

    The queue itself is chosen by app/infra.build_queue(): InMemorySourceScanQueue (a deque, used by the server) or AzureServiceBusSourceScanQueue (production, lock-token ack/abandon/dead-letter). Both dead-letter a job after MAX_QUEUE_ATTEMPTS.

    LLM assistance points¶

    LLM use in Layer 1 is analysis-only and always conditional on a gate decision. Each analyzer owns its prompts:

    Prompt (v1) Analyzer Purpose
    website_semantic_diff Website meaningful positioning shift vs noise
    careers_role_normalizer Careers classify job title → function
    careers_pattern_interpreter Careers hiring surge / geo expansion → signal
    news_relevance_resolver News is a borderline article about this competitor
    news_event_extractor News extract business event + signal_type
    blog_social_post_interpreter BlogSocial interpret a post → signal

    Extension points¶

    To add a source type you write an adapter package, an analyzer package, and register the type string in both registries. See the walkthrough in How-to: Add a New Source Type.
