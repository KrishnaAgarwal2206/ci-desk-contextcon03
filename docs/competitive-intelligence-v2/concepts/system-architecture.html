    System Architecture¶

    This page gives you the whole-system mental model for the Competitive Intelligence Aggregator: the three processing layers (scanning, intelligence, delivery), the admin control plane that drives them, the infrastructure abstractions that make the same code run locally or on Azure, and the telemetry that observes everything. Read it first — every other page in this section zooms into one part of the picture drawn here.

    The three layers¶

    The application is organized as a linear intelligence assembly line with three stages:

    • Layer 1 — Source scanning (app/adapters/, app/analysis/, app/workers/). For each configured Source, a source-type-specific adapter fetches raw data, persists it to blob storage and the database, and an analyzer diffs it against the previous scan and applies a cheap deterministic gate (plus optional LLM) to emit CandidateSignal rows. See Layer 1 — Source Scanning.
    • Layer 2 — Intelligence pipeline (app/intelligence/). A 15-step orchestrator turns raw CandidateSignal rows into deduplicated, classified, scored, and impact-assessed DetectedChange records, plus delivery artifacts and a cumulative CompetitorProfile. See Layer 2 — Intelligence Pipeline.
    • Layer 3 — Delivery (app/delivery/). The DigestAssembler builds the weekly digest from DetectedChange rows with status ready, and EmailDelivery / TeamsDelivery push it out. High-significance changes also trigger an immediate email alert from inside Layer 2.

    Control plane and admin¶

    Two entry points drive the layers, and both flow through the repositories layer (app/db/repositories.py) into the database — routes and workers never touch the ORM directly:

    • Config loader — app/admin/yaml_loader.py reads a competitor YAML (for example examples/config/godrej_competitors.yaml) and inserts Competitor and Source rows.
    • Admin panel + REST API — a single self-contained page at /admin/panel calls seven FastAPI routers under app/admin/ (routes.py, intelligence_routes.py, observability_routes.py, policy_health_routes.py, schedule_routes.py, scan_request_routes.py, news_profile_routes.py).

    Infrastructure abstractions¶

    Three capabilities are accessed through protocols so the same business code runs unchanged in either environment. The concrete implementation is chosen by app/infra.py based on ENVIRONMENT and the presence of connection strings:

    Capability Protocol Local Azure (production)
    Job queue SourceScanQueue InMemorySourceScanQueue AzureServiceBusSourceScanQueue
    Blob storage BlobStore LocalBlobStore (local://) AzureBlobStore (azblob://)
    LLM LLMProvider MockLLMProvider AzureOpenAIProvider

    The database follows the same idea: SQLite (WAL mode) locally, Azure SQL in production, both via SQLAlchemy.

    Runtime modes¶

    This is the single most important operational fact about the system, and it differs from older internal notes:

    In server mode nothing consumes the queue

    The only scheduler started by the FastAPI server (app/scheduler/__init__.py) is a WeeklyDigestScheduler (Layer 3 email, Mondays 08:00). It does not run source scans or the worker. Admin scan-requests only enqueue jobs. Actual worker execution is CLI-driven (ci-agent worker-once, ci-agent dev-run-once, ci-agent run-pipeline) or, in production, a separate process consuming Azure Service Bus. If jobs "aren't running," this is almost always why.

    Cross-cutting concerns¶

    • Telemetry — observe_agent() wraps every agent step in one AgentRunTelemetry row; runs roll up into CompetitorRun and PipelineRun. See Observability & Telemetry.
    • Cost ledger — each LLM call writes an LLMCostLedger row, propagated up the telemetry hierarchy. See LLM Abstraction.
    • Repositories — all persistence flows through app/db/repositories.py (roughly 80 functions); the CLI read commands are the only exception.

    verify=False is deliberate

    All adapter HTTP (and the permissive email SSL context) intentionally disables certificate verification to work behind the corporate proxy. This is a design decision, not a bug — do not "fix" it. See Configuration & Environment.

  storage/ queue/ scheduler/ workers/ admin/ feedback/ observability/

    Doc drift correction

    The real analysis package is app/analysis/ (not app/analyzers/), observability routes live in app/admin/observability_routes.py (not app/api/), and adapters/analyzers are organized as per-type packages (not flat *_adapter.py files). Where older notes disagree, the code wins.
