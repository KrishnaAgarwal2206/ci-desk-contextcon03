    Recover a Failed Run¶

    This guide shows you how to diagnose a scan that failed or got stuck, understand why, and re-drive it — by retrying failed sources, cleaning up stuck runs, or re-baselining a source. For the underlying error and retry semantics, see Error Handling, Retries & Status Codes.

    Prerequisites¶

    • A ScanRun that failed or has failed jobs.
    • The server running (for API/panel) or a checkout (for CLI).

    Step 1 — Find the failure¶

    Start at the run's jobs. Each SourceScanLog row carries the diagnostic fields.

    GET /admin/runs/{scan_run_id}/jobs

    Each job returns source_name, source_type, competitor_name, status (pending/running/success/failed/skipped), adapter_name, attempt_count, error_type, error_message, and candidate_signals_count. Look for status: failed and read error_type / error_message.

    In the panel: Admin Control → Runs, then drill into the run to see the per-job table. Common error_type values come from the worker (adapter/analyzer exceptions, NotFound for missing source/competitor).

    Note

    A job stuck at running with no update is usually an interrupted run (the process died mid-scan), not an active one. Startup marks orphaned running PipelineRun/ScanRun/AgentRunTelemetry rows as interrupted, but a run left over from a crash before restart may still show running — treat it as stuck (see Step 4).

    Step 2 — Understand the retry model¶

    The worker's retry behavior is asymmetric, which affects what "retry" means:

    • Pre-flight failures (e.g. adapter/analyzer not resolvable for the source type) call _fail_job, which marks the log failed and calls queue.retry. The queue increments the attempt count and dead-letters after MAX_QUEUE_ATTEMPTS (default 3).
    • Runtime failures (adapter or analyzer raises during scan/analyze) mark the job failed and ack the message — they are not retried automatically.
    • LLM failures never crash the job — the provider returns an LLMResult with error_message and empty output_json; the pipeline continues.

    Warning

    Because runtime adapter/analyzer failures ack (no auto-retry), a genuinely failed source scan will not re-run on its own. You must re-drive it explicitly with retry_failed (Step 3).

    Step 3 — Retry failed sources¶

    Re-enqueue only the failed SourceScanLog rows for a run:

    POST /admin/scan-requests
{
  "request_type": "retry_failed",
  "params_json": {"scan_run_id": "<failed_scan_run_id>"},
  "requested_by": "admin"
}

    Returns 202. Remember a worker must consume the re-enqueued jobs — run ci-agent worker-once locally, or rely on the prod consumer. See Run a Manual Scan.

    Step 4 — Clean up stuck runs¶

    If a run is wedged at running (crash, killed process), reset it so it no longer blocks visibility:

    POST /admin/scan-runs/cleanup

    This transitions running scan runs to abandoned. Restarting the server also marks orphaned running PipelineRun/ScanRun/AgentRunTelemetry rows as interrupted during startup.

    Step 5 — Re-baseline if needed¶

    If a source's stored state is corrupt or you changed its config such that diffs are meaningless, re-baseline it. This clears last_scan_at, so the next scan is treated as a first scan (baseline only, no signals) and subsequent scans diff against the clean baseline.

    POST /admin/scan-requests
{
  "request_type": "rebaseline",
  "params_json": {"source_id": "<source_id>"},
  "requested_by": "admin"
}

    Note

    The scan immediately after a rebaseline emits only a baseline and produces no candidate signals — that is expected. Run the source again to start seeing deltas.
