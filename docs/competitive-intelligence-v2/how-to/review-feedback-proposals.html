    Review & Approve Feedback Proposals¶

    This guide shows you how to work the human-review queue: list pending proposals mined from analyst feedback, understand their types and risk, and approve or reject them to activate policy. Approving a proposal is the gate that turns learned patterns into live suppression rules, weight profiles, or agent policy rules. For the full governance lifecycle, see Feedback & Learning Governance.

    Prerequisites¶

    • Analyst feedback has been submitted on DetectedChange rows, producing proposals. See the first feedback loop tutorial.
    • The server running (for API/panel).

    Governance never auto-approves

    The governance pipeline is deterministic and never activates policy on its own. Every proposal sits at pending_human_review until a human approves it. (The legacy path may apply some effects immediately — that is separate; see Manage Suppressions.)

    Step 1 — List pending proposals¶

    GET /admin/feedback/proposals?status=pending_human_review&limit=50

    Returns the newest 50 proposals. In the panel, use Governance → Governance (the screen shows a red badge with the pending count and approve/reject controls).

    Step 2 — Understand proposal types and risk¶

    Proposals are generated deterministically from mined patterns (_PROPOSAL_THRESHOLD=2). There are three builders:

    Proposal type Generated when Risk
    suppression_rule verdict false_positive — every occurrence (not frequency-gated) low (≤2), else medium
    scoring_weight_change over_scored/under_scored, frequency ≥ 2, category present (±10%) high
    agent_policy_rule misclassified, wrong_geography, weak_evidence_overpromoted, false_positive, over_scored, under_scored, frequency ≥ 2 medium

    Dual proposals

    An over_scored/under_scored pattern at frequency ≥ 2 produces both a scoring_weight_change and an agent_policy_rule proposal (both targeting the scorer). Expect to review two related proposals, and decide on each independently.

    The agent_policy_rule builder retargets by error type (e.g. misclassified → classifier, over_scored/under_scored → scorer), ignoring the feedback's own agent_name.

    Step 3 — Approve or reject¶

    Only pending_human_review proposals can be approved.

    POST /admin/feedback/proposals/{id}/approve
{
  "reviewer": "krishna",
  "edited_change_json": null
}
    • Approving as-is sets status approved. Supplying edited_change_json sets status edited_and_approved and activates the edited version.
    • Reject instead:
    POST /admin/feedback/proposals/{id}/reject
{
  "reviewer": "krishna",
  "review_notes": "Legitimate event, not noise"
}

    Warning

    Approval always activates, regardless of the proposal's risk_level. There is no separate "approve but hold" — approving a high-risk weight change activates it immediately. (REQUIRE_HUMAN_APPROVAL_FOR_PROMPT_CHANGES only gates auto-activation, not this manual approval.)

    Step 4 — What activation does per type¶

    _activate_proposal dispatches by proposal_type:

    • suppression_rule → _activate_suppression: creates one active SuppressionRule per all_values entry (dedupes on already-active values).
    • scoring_weight_change → _activate_weight_change: deep-copies the active weight profile, applies the new category_scores[cat], deactivates the old profile, inserts a new active ScoringWeightProfile (feedback_adjusted_<cat>).
    • agent_policy_rule → _activate_policy_rule: creates an active AgentPolicyRule and auto-recompiles that agent's default policy pack via PolicyCompiler().compile_pack().

    Step 5 — Verify runtime state¶

    Confirm the change is live:

    GET /admin/feedback/runtime-state

    This shows the currently active rules, packs, weights, and suppressions. In the panel, Governance → Runtime State renders the same live view.
