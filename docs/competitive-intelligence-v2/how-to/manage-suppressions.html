    Manage Suppressions¶

    This guide shows you how to create and remove suppressions so noisy URLs, domains, or repeat events stop generating signals and changes. The system has two independent suppression subsystems — a legacy one that acts in Layer 1 and a governance one that acts in Layer 2 — and you need to know which one you are touching. For the governance model overall, see Feedback & Learning Governance.

    Prerequisites¶

    • The server running (for API/panel) or a checkout (for CLI).
    • A URL, domain, or event you want to stop seeing.

    Two suppression systems — not unified

    These two tables are separate and enforced at different points. Creating one does not affect the other.

    Legacy (Layer 1) Governance (Layer 2)
    Model FeedbackSuppressionEntry SuppressionRule
    Code app/intelligence/feedback.py app/feedback/suppression.py
    Enforced at source_scan_worker.py + news analyzer (Layer 1) Layer 2 orchestrator
    Created via direct API/CLI proposal approval
    Supports title_pattern; domain is a note only source_url, domain, event_fingerprint

    Legacy suppression (Layer 1)¶

    Legacy entries stop candidate signals from being generated during scanning. They are checked in the scan worker and the news analyzer via get_active_suppressions / is_suppressed.

    Create a legacy suppression¶

    POST /admin/feedback/suppressions
{
  "value": "https://example.com/press/holiday-notice",
  "reason": "Recurring low-value holiday post"
}

    List and delete:

    GET    /admin/feedback/suppressions?active_only=true&limit=50
DELETE /admin/feedback/suppressions/{id}

    Via CLI:

    ci-agent feedback-suppressions --limit 50

    Legacy entries can match a title_pattern; domain-level suppression here is only recorded as a note, not enforced as a domain block.

    Governance suppression (Layer 2)¶

    Governance SuppressionRule rows gate the Layer 2 orchestrator: is_candidate_signal_suppressed (URL then domain) and is_event_suppressed (change:<id> fingerprints). They are not created directly — they come from approving a suppression proposal.

    Create a governance rule via proposal¶

    1. Submit false_positive feedback on a DetectedChange. This generates a suppression_rule proposal (created on every false-positive occurrence — not frequency-gated). See Review & Approve Feedback Proposals.
    2. Approve the proposal. _activate_suppression creates one active SuppressionRule per all_values entry (deduping on already-active values).

    Shortcut: if AUTO_CREATE_EXACT_URL_SUPPRESSION is enabled, a false_positive verdict also creates an exact-URL SuppressionRule immediately as a structural action (in addition to the proposal). AUTO_ARCHIVE_FALSE_POSITIVE similarly archives the change immediately.

    List active rules:

    GET /admin/feedback/suppression-rules

    Suppression types & TTLs¶

    Governance rules come in three types, with default expiry governed by config flags:

    Type Matches Default TTL flag Default
    source_url exact URL DEFAULT_SUPPRESSION_EXACT_URL_TTL_DAYS None (never expires)
    domain whole domain DEFAULT_SUPPRESSION_DOMAIN_TTL_DAYS None (never expires)
    event_fingerprint a specific event (change:<id>) DEFAULT_SUPPRESSION_EVENT_FINGERPRINT_TTL_DAYS 90

    Rules respect expires_at; expired rules stop matching. Domain suppressions require human approval (REQUIRE_HUMAN_APPROVAL_FOR_DOMAIN_SUPPRESSION=True).

    Where each is enforced¶

    • Legacy FeedbackSuppressionEntry — Layer 1, during scanning (worker + news analyzer). Stops candidate signals at the source.
    • Governance SuppressionRule — Layer 2, inside the orchestrator. Stops candidate signals from being promoted and suppresses already-detected events.

    To fully silence a noisy source across both layers, add a legacy entry and a governance rule.

    • Review & Approve Feedback Proposals to approve the suppression-rule proposals that create governance rules.
