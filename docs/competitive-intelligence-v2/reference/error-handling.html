    Error Handling, Retries & Status Codes¶

    This page documents how the system behaves when things fail: how the Layer 1 worker fails and retries jobs, how LLM calls degrade without crashing, which HTTP status codes the admin API returns, how orphaned runs are reclaimed on startup, and the common error_type values you will see in the logs. It is a reference companion to Recover a Failed Run.

    Worker error paths¶

    The Layer 1 worker (app/workers/source_scan_worker.py, SourceScanWorker.process_job) distinguishes two failure classes, which behave asymmetrically on the queue:

    • Pre-flight failures (before the adapter runs) — e.g. the adapter or analyzer for a source_type cannot be resolved. These call _fail_job, which marks the SourceScanLog failed and calls queue.retry. The queue increments the job's attempt count and re-delivers it, dead-lettering after MAX_QUEUE_ATTEMPTS (default 3).
    • Runtime failures (during adapter or analyzer execution) — an exception thrown while fetching or analyzing. These mark the log failed, update scan timestamps to failed, and queue.ack the job (no retry).

    Warning

    This ack-vs-retry asymmetry is deliberate but easy to misread: a missing adapter/analyzer registration is retried and eventually dead-lettered, whereas an exception inside a working adapter is acknowledged and not retried. A source that fails at runtime will not re-run on its own — re-drive it with a retry_failed scan request or the next scheduled scan.

    A missing source/competitor is a terminal case: the log is marked failed with a not-found error, the job is acked, and process_job returns False.

    Dead-lettering¶

    The queue (InMemorySourceScanQueue locally, AzureServiceBusSourceScanQueue in production) increments attempt on each retry and moves the job to the dead-letter path once attempt exceeds MAX_QUEUE_ATTEMPTS. Tune the threshold with the MAX_QUEUE_ATTEMPTS setting — see Configuration & Environment.

    LLM failure semantics¶

    Warning

    LLM failures never crash the pipeline. The provider (AzureOpenAIProvider) wraps every call in try/except and always returns an LLMResult — it never raises.

    On failure or degradation the provider returns an LLMResult with:

    • error_message set (populated for content-filter blocks and length-truncation cases), and
    • output_json empty ({}); non-JSON model output is returned as {"raw_text": ...}.

    Because analyzers and the Layer 2 orchestrator treat an empty output_json as "no LLM contribution," a failed LLM call degrades gracefully to the deterministic path rather than aborting the run. Each call is still recorded as an LLMTrace (with the error_message) and a cost-ledger row. See LLM Abstraction.

    HTTP status codes¶

    The admin API (all routers under app/admin/) uses conventional REST status codes. Error bodies follow the Error("<status>: <text>") convention.

    Code Meaning Typical endpoints
    200 Success (reads, updates). Most GET/PATCH/PUT endpoints.
    201 Created. POST /admin/competitors, .../sources, POST /admin/scan-runs, schedule/news-profile create, POST /admin/incidents, proposal/eval/pack creation.
    202 Accepted — work runs in the background. POST /admin/scan-requests (dispatches _run_scan_in_background).
    204 No content — soft delete. DELETE /admin/competitors/{id}, .../sources/{id}, .../schedule, news-profile delete.
    400 Bad request. e.g. GET /admin/observability/costs with an invalid group_by.
    404 Not found. GET /admin/competitors/{id}, .../scan-runs/{id}, .../runs/{id}, schedule/news-profile/coverage-map lookups, etc.
    409 Conflict — resource already exists. POST /admin/sources/{id}/schedule when a schedule exists; news-profile create when one exists.
    422 Unprocessable — invalid enum/payload. POST /admin/detected-changes/{id}/feedback with an invalid verdict.

    Note

    POST /admin/scan-requests returns 202, not 201: it enqueues work and returns immediately. In server mode nothing consumes the queue automatically, so a 202 means "accepted and enqueued," not "executed." A worker or Service Bus consumer must run for the jobs to complete.

    Orphan / interrupted marking on startup¶

    On application startup (app/main.py) the app marks any PipelineRun, ScanRun, and AgentRunTelemetry rows still in a running state as interrupted. This reclaims runs left dangling by a crash or an abrupt shutdown so the observability views do not show perpetually "running" work. (Startup uses the deprecated on_event hook rather than the newer lifespan API.)

    The scan-run cleanup endpoint POST /admin/scan-runs/cleanup performs a related manual reclamation, transitioning stuck running scan runs so they no longer block the console.

    Common error_type values¶

    SourceScanLog.error_type and error_message capture the failure reason for a source scan. Common error_type values include:

    • NotFound — the source or competitor could not be loaded.
    • Adapter/analyzer resolution failures — no adapter or analyzer registered for the source_type.
    • Adapter runtime exceptions — network/parse errors raised during fetch (surfaced with the exception text in error_message).
    • Analyzer runtime exceptions — errors raised during analysis.

    Inspect these per job via GET /admin/runs/{id}/jobs (each row resolves source_name, status, attempt_count, error_type, error_message) or with ci-agent list-scan-runs and the panel's Runs screen.
