    Tutorial — Your First Scan (Layer 1)¶

    In this tutorial you will run Layer 1 end-to-end on your machine and read the candidate signals it produces. Layer 1 is the ingestion stage: for each configured source it fetches content, persists raw and normalized data, diffs against the previous scan, and runs an analyzer that emits CandidateSignal rows — the input to Layer 2.

    Prerequisites¶

    • You completed Configuration & First Config Load — competitors and sources are loaded.
    • Your virtual environment is active.
    • You are running offline with the mock providers (the default), so no keys are needed.

    1. What Layer 1 does¶

    For each due Source, Layer 1 dispatches a source-type-specific adapter to fetch content, persists the results (RawArtifact, NormalizedDocument, DocumentBlock, SourceItem), then runs an analyzer that applies a cheap deterministic gate and — only when needed — an LLM call, producing LowLevelDelta → ChangePackage → CandidateSignal. For a deeper explanation, see Layer 1 — Source Scanning.

    Note

    The first scan of any source establishes a baseline — it records what exists but emits only a baseline_created delta and no candidate signals. Signals appear from the second scan onward, when there is a previous state to diff against. This is expected.

    2. Run the scan¶

    dev-run-once is the canonical local command for a full Layer 1 run. It scans all due sources and prints a summary table.

    ci-agent dev-run-once
# equivalent: python -m app.cli dev-run-once

    3. Read the summary table¶

    The command prints a per-source summary: which adapter and analyzer ran, how many artifacts, documents, and items were persisted, and how many candidate signals were produced. On the first run, expect signal counts of zero (baseline). Run it a second time to see change-driven signals appear.

    4. Inspect the signals¶

    List the candidate signals the scan produced:

    ci-agent list-candidate-signals --limit 20
# add --verbose for more detail, or filter with --status / --type

    Then drill into a single signal by ID:

    ci-agent show-signal <signal-id>

    Each signal carries a signal_type, a preliminary category, a title and summary, entities, evidence, a confidence score, and whether an LLM was used (llm_used).

    5. What just happened¶

    The scan worker ran this chain for each source:

    1. Adapter fetched the source and returned artifacts, normalized documents, and discovered items.
    2. The worker persisted raw artifacts to the blob store and normalized documents/items to the database.
    3. The analyzer loaded the previous state, computed deterministic deltas, and ran the cheap gate — which decides per change: suppress noise, promote as a candidate without an LLM, or send for llm_review.
    4. For llm_review changes, the analyzer called the LLM; otherwise it built the signal deterministically.
    5. Results were persisted as CandidateSignal rows with status candidate.

    For the full 12-step worker flow and the adapter/analyzer patterns, see Layer 1 — Source Scanning.
